# 標準開発手順

版：0.1。DDPTの既存[AI協働開発標準](https://github.com/mnakagaw/DDPT-TOP/blob/6d2aee5f767515c5b20118ed642f832f21a15151/docs/AI_ASSISTED_DEVELOPMENT_STANDARD_JA.md)を基礎に、操作の忠実性、国別適応、実務の受入を加える。

## 1. 作業の入口

最初に対象国、目的、作業場所、公開までの依頼範囲、参照版、現地の担当を特定する。AIが既存資料から開始シートを埋め、結果を大きく変える不明点だけ確認する。資料が不足していても、独立した調査・構造化・検証は進める。

| 段階 | 作業 | 成果と通過条件 |
|---|---|---|
| 0 基準確認 | DDPTの参照commit、公開版、既知の所見、作業中の変更を区別する | 参照台帳。修正前のDDPT不具合を世界仕様として固定しない |
| 1 国別調査 | 現地業務、制度、地域・境界、資料、権限、回線、更新体制を確認する | 開始シート・出典台帳・未確定事項と担当 |
| 2 適応設計 | 各ページをDDPTの対応ページへ対応づけ、機能の採用・代替・保留を決める | 共通仕様からの差分と理由。データ不足をUI再設計の口実にしない |
| 3 基準画面 | 同じ地域・条件・表示幅で、構成図と比較画像を作る | 操作、情報の優先順位、取得ボタンが具体的にレビューできる |
| 4 一連の実装 | データがある地域・不足する地域で、診断→比較→資料→出力を通す | 画面モックだけでなく、実データと実際の取得物で成立する |
| 5 全国展開 | 全対象・同名・独立市・境界変更・欠測・遅い応答へ広げる | 未結合と対象外を記録。検索・一覧から到達可能 |
| 6 検証・レビュー | データ、操作、画面、文書、保存・復元を検査する | Task Contractと受入台帳の対応。独立レビューで逸脱を確認 |
| 7 利用者確認 | 現地担当者が代表タスクを実行する | 完了率、迷う操作、誤読、時間、支援の必要箇所を記録し、重要な問題を解消 |
| 8 版固定・公開 | 指定範囲をGit・CI・成果物・公開先に結び付ける | 対象版、限定マニフェスト、バックアップ、公開後の同じ操作の確認 |
| 9 運用・改善 | 更新、障害、出典改訂、利用者の不具合を管理する | 担当・頻度・手順。共通改善と国別差分を分けて次版へ |

この手順を一度に全機能へ適用せず、完成する利用業務の単位で区切る。表の各段階は原則として追加の許可を要求する地点ではなく、成果を確認する地点である。

## 2. AIによる意図しない変更を防ぐ

AIへの依頼に「DDPT風」「使いやすく」だけを書かず、次を渡す。

- 対応するDDPTのページ・参照commit・画面状態。
- C01～C07の守る挙動と、具体的な成功シナリオ。
- 国別に変更できる範囲、資料条件による代替規則。
- 現在のURL・保存データ・出力の互換性条件。
- 既知の不具合のうち修正するものと、今回触らないもの。
- 完了地点と、合否を判断できる画像・取得物・検証記録。

実装前の比較表は「現行／変更後／理由／対象利用者への影響／検証」を１行ずつ記す。実装後には同じ表で実際の差分を確かめる。合理的な改善提案は別欄に残し、合意していない主要導線変更へ混ぜない。

通常の修正は既存の意図と規則に従って進める。共通モデルの目的、主要な操作、集計の意味、権限、保存互換性を変える場合に限り、その具体的な結果を判断対象にする。新しい承認を毎回取り直すことは標準化の目的ではない。

## 3. 検証の組み立て

- **データ**：コード一意性、境界結合率、欠測、分子・分母、重複、版と日付、原表と代表値の照合。
- **操作**：C01～C07とF01～F09を代表シナリオに結び付け、地域切替・共有・戻る・検索・出力・失敗復旧を検証する。
- **画面**：DDPT対応画面と同条件で比較し、情報配置・最初に見える分析領域・章移動を確認する。色だけの一致で閉じない。
- **文書**：実際に取得したファイルを読み、地域・期間・単位・数値・出典・草案表示・図の意味を確認し、隔離レンダラーで改ページや欠けを点検する。
- **保存**：旧形式のメモ、再読込、バックアップ・復元、読込失敗、別地域との分離を検証する。
- **利用環境**：狭い画面、キーボード、200%文字拡大、想定回線、現地語で主要タスクを完了する。

文言・余白だけの軽微な変更に実装をなぞるテストを追加しない。報告された不具合、データの意味、複数画面の連動など再発すると困る部分には有効な自動回帰検査を置く。未実施のブラウザ・認証・文書検証を自動テストの成功件数で代替しない。

現地利用者テストは、少人数から問題を見つける目的で始める。添付報告書の５～８人という案は探索用の出発点であり、全利用者への有効性を保証する人数ではない。役割・端末・地域条件の違いを含める。

## 4. Gitと公開

1. 既存変更と対象範囲を確認し、必要なら独立した作業ツリーを作る。
2. 指定した変更だけをcommitする。新しい国のリポジトリ作成・公開は、その案件で決めた範囲に従う。
3. 対象commitからビルド・検証し、push・必要CI・リモートSHAを確認する。
4. 公開対象のパス・事前hash・新hash・順序・復元方法をマニフェストに固定する。
5. 現在の公開版と競合していないか照合し、バックアップを取る。公開先の仕組みに応じて検証した成果物を反映する。
6. 公開URL・参照資産・取得物・代表操作を確認する。必要に応じてhashを再取得して照合する。
7. Local／GitHub／Hosting／Publicと、残る制約を分けて報告する。

DDPT型のFTPS公開を採用する案件では、証明書検証付きの明示的FTPS、仮ファイル転送と再照合、競合確認、資産を先・HTMLを最後、失敗時の復元を使う。国ごとのホスティング方式は固定しないが、版との対応・対象範囲・復元・公開後確認は共通化する。

## 5. 運用と共通モデルの更新

公開後は出典・地域対応・指標・文書・共通コアに責任者を置く。同一人物が兼務しても、更新すべき項目が分かる台帳にする。取得者が自動的に公開内容を決める構造にはせず、検証済みの版を反映する。

不具合は、共通コアの問題、国別制度・表示の問題、出典・アダプターの問題に切り分ける。共通修正には互換性と国別の影響を記し、代表検証を通した国から適用する。

共通仕様のメジャー版は主要な操作・意味・互換性を変える場合、マイナー版は互換性を保つ機能追加、修正版は不具合修正を目安にする。国別設定とデータ版も独立に記録し、画面と文書がどの版で作られたか追跡する。

## 6. この0.1の次の実装順

1. F01～F03の対象版を再確認し、改善後のDDPT共通基準を決める。
2. F04～F09とウガンダの教訓を反映した代表画面・受入例をそろえる。
3. 最初の共通部品候補として、地域選択とURL、対象範囲の表示、出典・状態、取得ボタンを抽出する。
4. ドミ共とウガンダの異なる条件で同じ操作が成立するか試し、共通化が過剰な箇所を国別へ戻す。
5. 具体的な次の国の開始シートを使い、全国展開前に一連の利用業務を完成させる。

これは今後の実装手順であり、このターンで既存サイトの修正・ライブラリ化が実行されたという報告ではない。
